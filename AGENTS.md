# AGENTS.md

Usage, building and releasing are in README.md. This file holds the architecture and what the code does not say.

- **`web/vendor/JIZURA` is upstream JIZURA as a submodule — never edit it.** The page loads its `src/*.js` directly as classic scripts (global `J`); `tools/update-jizura-scripts.sh` writes the `<script>` list into `web/index.html` between the `jizura:begin` / `jizura:end` markers, in byte order (`LC_ALL=C`, matching upstream's `sorted(glob)`), minus `12_ui.js`. Change what JIZURA does through the project / plan values `app.js` passes in, not by patching it.
- **JIZURA's renderer is a pure function of time.** Sync is `frame(ctx, plan, positionMs + offsetMs)` every animation frame; there is no sync state to keep.
- **Drawing cost and the quality ladder (`app.js` `QUALITY`).** Some cuts cost far more than a frame: measured 2026-10-16 in the Windows app (Radeon 780M, 120 Hz, 1440 px canvas), `cylinder` / `glitchGrid` cuts took 30–200 ms of main-thread time per frame, almost all of it Chromium serialising text draws for the GPU (`RasterImplementation::RasterCHROMIUM`) — glyphs at a new size every frame, × 3 for the chromatic ghost passes; the GPU itself was idle. `--disable-accelerated-2d-canvas` made it 3–80× slower. So `tick()` steps down while frames come late (`fast` → 0.75× canvas → `noGhost` → 0.5× → 30 fps; `fast` and `noGhost` are JIZURA's own `frame()` options) and back up after 3 s with no late frame. Late = the next animation frame came over 1.5× the due interval; a cut's first frame and the 1.5 s after a new plan or font are not judged (cache building no level makes cheaper). The drawn time is floored to the plan's 60 fps grid, so a 120 Hz display draws every other frame. `?quality=N` pins a level; `jizuraSync.perf` shows level, canvas size and frame time. `SyncRenderer` keeps the previous cut's resting frame in `transA` across a transition (JIZURA redraws it every frame at one fixed time; transitions only read it) — same pixels, so this is not a patch of JIZURA's output.
- **JIZURA settings that matter here:** `unify` defaults off upstream and its random look (`J.omakase`) never sets it, which makes every cut an independent draw; it is on by default here (`U`). `fx.koma` (frame stepping) is chosen per mood by `omakase`; `K` overrides it.
- **Section breaks feed `unify`.** JIZURA ends a part at an empty lyric row or a `[間奏]` line; `lyrics.js` `partBreaks()` inserts empty rows from LRC blanks, long pauses and repeated blocks, then merges parts under 3 lines and splits parts over 8. It was tuned on LRCLIB data for four songs — re-check part sizes (`lines … in … parts` in the console) when changing it.
- **LRCLIB** asks clients to identify themselves (`Lrclib-Client` header, allowed by its CORS preflight) and to honour `Retry-After` on 429. It also has short outages: `/get` and `/search` answered 503 several times on 2026-09-29, so 5xx and network failures are retried after 2 s and 5 s. A hit must be within `DURATION_TOLERANCE_S` (4 s) of the player's length; re-releases such as "Blue Flame (2023 Ver.)" often have synced lyrics only for a version 5–12 s longer or shorter, and show "No lyrics found". That is a matching limit, not a bug.
- **Other lyric sources (`lyrics.js` `SOURCES`, added 2026-10-18 because LRCLIB lacked many songs):** all are asked at once and the first in the order LRCLIB → PetitLyrics → lrc.red → NetEase with synced lyrics wins (the user's order: LRCLIB first so Western songs stay as they were, PetitLyrics second because it is strongest on Japanese songs). Once a lower source has synced lyrics, a higher one still pending gets 3 s (`HIGHER_WAIT_MS`) — LRCLIB's 2 s + 5 s retries otherwise held every song for 7 s+ while it answered 503. The lookup throws only when every source failed, so a third-party outage shows "No lyrics found", not "lookup failed". Every hit must pass `matches()` (length, base title, a shared artist, no cover / live / karaoke word the player's title lacks): lrc.red answers 米津玄師「Lemon」 with covers by 花僮 and 洛天依 at 257 s. **PetitLyrics** (プチリリ, a Japanese lyrics service) is reached through its Android SDK's `GetPetitLyricsData.php` with that SDK's `clientAppId` (`CORS *`); `lyricsType=3` is word timing (`<wsy>`, base64), and an empty `<line>` is a section break, which becomes an empty LRC row. A search lists up to `maxCount` user-posted records but carries lyrics only for the first; another one is fetched again by `key_lyricsId`. **lrc.red** (found through am-lyrics) gives Apple Music style TTML by ISRC (`CORS *`); each `<div>` is a song part. Its text uses Kangxi radicals for some kanji (「⼆⼈」「⽇」), so `lrcToJizura` folds U+2E80–U+2FDF with NFKC for every source. **NetEase** sends no CORS headers, so only the Windows app asks it: the page posts `{cmd: 'http', id, url, form}` and the host answers `{http: id, status, body}` or `{http: id, error: host | timeout | network}` (`MainForm.Fetch`; error kinds, like the readings), for https URLs on `HttpHosts` (`music.163.com`) only and without following redirects, so the page is no general proxy. A new track aborts the previous lookup (`app.js` `lookup`), and a lookup that has its answer aborts the sources still running, so LRCLIB's retries stop with it; an aborted `nativeHttp` only drops the host's answer (the host still finishes the request). Its LRC opens with credit rows (「作词 : …」), dropped up to the first sung row. `?lyrics=lrclib|petit|lrcred|netease` asks one source alone; `jizuraSync.song.source` and the `lines … in … parts (source)` console line show which one was used.
- **Lyric sources tried and left out (2026-10-18).** Coverage measured over 70 songs, a hit counting only when artist, title and length (±4 s) match. Of 40 mid-tier / Vocaloid / idol / Showa–Heisei Japanese songs, PetitLyrics had word-timed lyrics for 34, NetEase line-timed for 35, lrc.red for 18. Of 30 popular songs (22 Japanese, 8 Western), LRCLIB had 29, NetEase 28, PetitLyrics 25, and lrc.red all 8 Western ones. LRCLIB itself answered 429 / 503 during the 40-song run. Left out: Apple Music directly and Manzana (searching works with the developer token in music.apple.com's `index~*.js` — it now starts `eyJ0`, which Manzana's and SongSync's `eyJh` patterns miss — but lyrics need a subscriber's `media-user-token`, and the user has no subscription); SongSync's paxsenix proxy (503); Musixmatch's desktop API (`token.get` gives an all-zero token, and searches then return a decoy track "NOKIA" with nonsense lyrics); LyricsPlus / KPoe (3 of 4 mirrors 402 / 404, the last one 429); Kugou (overlaps NetEase, added 2 songs); QQ Music search (500).
- **Why this is not a public service:** LRCLIB lyrics are unlicensed community data; PetitLyrics is used through another app's ID, and lrc.red and NetEase are unlicensed too. That caveat applies to any build shared from this repo. This repo must also never contain LSE-Core / COTODAMA code or names.
- **Lyrics offset sign:** the renderer draws `positionMs + offsetMs`, so a positive offset shows lyrics *earlier*. `]` is +50 ms (earlier), `[` is −50 ms (later).
- **Now-playing bar:** it hides with the cursor once the pointer has rested for 3 s (`IDLE_MS`, the `idle` body class) and comes back on any pointer move or key; not while the pointer is on it, the seek slider is dragged or Tab has moved focus into it (`tabbed`, cleared by any pointer press). Not `:focus-visible`: a clicked button keeps focus and turns `:focus-visible` at the next key press (checked 2026-10-18), which held the bar up for good. The pin button / `H` keeps it shown (`jizura-sync.barPinned`, localStorage); a click outside it hides it at once. This replaced click-to-hide (`jizura-sync.barHidden`, which stuck until the next click) on 2026-10-18 at the user's request. The bar is `inert` while hidden, so its controls leave the tab order; `keydown` wakes it before Tab moves focus. The status line lives inside the bar, so errors go through `showError()` → a toast outside it, once per distinct message while there is no playback state. Why a song has no lyrics goes to `#notice` in the middle of the window instead, and gets no toast (the two said the same thing); the notice is centred with `inset: 0; margin: auto`, because `translate(-50%, -50%)` lands on half pixels and blurred its text in WKWebView (upstream's Mac app). Popping the whole bar up on every status was tried and reverted: with no device it stayed up permanently, so `setStatus` does not wake it (a key that sets a status does). A control's feedback (offset, `U`, `K`, the pin) goes through `flashStatus`, which holds the line for 3 s and then puts back the latest `setStatus` text (source · style · mood · cuts, or an error); before 2026-10-18 it replaced that line until the next song. A click hides the bar after 250 ms so a double click (fullscreen) does not flash it. The global keydown guard skips text inputs only; a focused range input (the seek slider) must not swallow shortcuts.

- **Windows app (`win/Program.cs`, `tools/build-win.ps1`):** WinForms + WebView2 around `web/`, playback from the system media sessions (Global System Media Transport Controls) instead of upstream's Spotify Web API, so it follows any player, browser tabs included (the user's choice, 2026-10-16). `native.js` treats `window.chrome.webview` (present only inside a WebView2 host) as the native bridge: commands go out with `chrome.webview.postMessage`, readings come back through `PostWebMessageAsJson` as `{seq, source, playing, positionMs, track}` or `{seq, error: {kind: idle | script | transient, app, apps, detail}}` — error kinds and app names, never sentences. Commands carry a `seq` and readings echo the last seq processed, so a reading started before a command is dropped; the bridge resets its count on each page load. The page is served at `https://app.jizura-sync.test/` by `SetVirtualHostNameToFolderMapping` — that origin owns the page's localStorage, so never change it. Session choice: playing before paused, then the one followed last, then Windows' current session; a session with no title is skipped. Position is `Position − StartTime`, plus `now − LastUpdatedTime` while playing; a length of 0 is the stream path. GSMTC has no track ID, so `trackId` is app ID + title + artist + album + length in seconds: a player that fills in the length after the title gives a new track, which re-fetches lyrics. The window cannot see mouse presses on the page (WebView2 owns them), so the page sends `dragWindow` once a press outside the bar / help has moved 3 px, and the host runs Windows' own move loop (`ReleaseCapture` + `WM_NCLBUTTONDOWN`/`HTCAPTION`); a press that does not move stays a click. Fullscreen is the host's, not HTML fullscreen: in HTML fullscreen WebView2 leaves fullscreen on Esc before the page sees the key, and neither Keyboard Lock (`navigator.keyboard.lock(['Escape'])`) nor `Handled` on the WinForms control's `KeyDown` stopped it (checked 2026-10-18), so Esc could not close the help first. The page sends `{cmd: 'fullscreen', on}`, with no `on` (F, the button, double-click) the host flips its own state, so two quick presses are not both "on". The host sizes its borderless window over the monitor and posts `{fullscreen: bool}` on every change; Esc closes the help, then leaves fullscreen. Any navigation (F5) leaves fullscreen, since a page that fails to load has no Esc. Measured 2026-10-16 with a Chromium tab (the desktop app's browser pane, a silent test page): every seek, play and pause posts `TimelinePropertiesChanged` and/or `PlaybackInfoChanged`; a session disappears when its media ends; the paused position is whatever the page last gave `setPositionState` (a page that sets it only on seek reports a stale one — Chromium's own reporting, with no `setPositionState`, was exact). A browser applies a seek after `TryChangePlaybackPositionAsync` returns (its `seekto` handler runs in the page), so readings after a seek carry the seq before it until the timeline lands on the target or 1 s passes; without that the slider jumped back for ~0.8 s against a handler that seeks 400 ms late. `SetThreadExecutionState` is per thread, so it is only called on the UI thread. Each WinRT call has a 2 s timeout, because a session belongs to another process. This repo is Windows-only (`mine` = Fuku856/jizura-sync-windows, `origin` = upstream Saqoosha/jizura-sync): the Mac app — `mac/`, Sparkle, upstream's Developer ID signing, notarization and release scripts, and the page's WKWebView bridge — was removed on 2026-10-16 (the user's decision). Upstream's Spotify Web API page (`web/spotify.js`, the Client ID gate, `serve.sh`'s Redirect URI) and its Tesla support (`tools/deploy-cloudflare.sh`, tap keys in the help) were removed on 2026-10-18 (the user's decision): playback comes only from the media sessions, which already cover Spotify and Apple Music, and a plain browser shows a notice unless `?mock` is given. An upstream change to `mac/`, `web/spotify.js` or `tools/deploy-cloudflare.sh` comes in as a modify/delete conflict — keep the deletion; conflicts in the Spotify / Tesla parts of `app.js`, `index.html`, `style.css` and `i18n.js` resolve the same way. `build-win.ps1` leaves JIZURA's `10_audio.js` / `11_export.js` (editor-only) out of the copied `index.html` and copies only the JIZURA scripts that file loads (so not `12_ui.js`). The build is one framework-dependent exe (`PublishSingleFile`) beside `WebView2Loader.dll` and `web/`, about 5 MB in all (28 MB before 2026-10-17). Most of that saving: the TFM is `net10.0-windows` with no Windows version, because a versioned TFM references the SDK's projection of the whole Windows API (`Microsoft.Windows.SDK.NET.dll`, 25 MB); C#/WinRT projects only the namespaces in the csproj's `CsWinRTIncludes` from the `.winmd` files of `Microsoft.Windows.SDK.Contracts` (no Windows SDK install needed). A WinRT type outside that list does not compile until it is added, and whatever it references must be added or excluded too; `Windows.Storage` and `Windows.ApplicationModel` pull in most of the API, so the app name comes from the shell (`shell:AppsFolder\<AUMID>`) instead of WinRT's `AppInfo` — same name for the desktop app's browser pane, checked 2026-10-17. `win/.editorconfig` silences nullable warnings in the generated projection. The minimum OS (19041) is written as an assembly attribute in the csproj, since `SupportedOSPlatformVersion` cannot exceed the TFM's version. Minimized, the page is `hidden` and animation frames stop (checked 2026-10-16), so the host does nothing extra for it.

- **Icon:** `win/icon.png` (1024 px, upstream's art) is the source; `tools/make-win-icon.ps1` writes `win/app.ico` from it. The art is full-bleed with no padding of its own, so the script clips it to a rounded square. It was drawn by a script (Hiragino Sans W9 「字」 with RGB split, torn strips and noise); image generation mangled the character once the glitch was strong. Thick strokes only — hairlines vanish at small sizes.
- **Japanese UI:** `web/i18n.js` holds every UI string, keyed by its English text (`t('… {var}', vars)`, `data-i18n*` attributes in `index.html`). The native bridge sends error kinds and app names, never sentences, so all wording stays in one file. In the Windows app, `navigator.language` is WebView2's default: Windows' display language.
- **Commits and PRs are written in Japanese, with no emoji** — no gitmoji prefix (the user's rule from 2026-10-17). Earlier history, through PR #6, and upstream still use English gitmoji; do not copy that style. PR titles become the "What's Changed" lines of the release notes, so write them as changelog entries.

## Checking changes

- Windows app: `tools/build-win.ps1`, then run `build\win\jizura-sync.exe` with `JIZURA_WEB_ROOT=<repo>\web` (F5 reloads), `JIZURA_QUERY=mock=Artist|Title|durationMs&t=30`, and `JIZURA_LOG=<file>` (every reading and session event). `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` opens CDP on the page (`http://127.0.0.1:9333/json`); fullscreen is the button's `click()`. CDP's `Input.dispatchKeyEvent` skips the paths real keys take (it ignored a Keyboard Lock that held a real Esc); to send a key without touching the user's foreground window, post `WM_KEYDOWN` / `WM_KEYUP` to the app's `Chrome_RenderWidgetHostHWND` child. To test a session without touching anyone's player, play a silent `<audio>` with `navigator.mediaSession.metadata` in a browser tab; `python -m http.server` has no Range support, so load the audio as a Blob URL or seeking snaps back to 0. Window captures and `GetWindowRect` from PowerShell need `SetProcessDpiAwarenessContext(-4)` first: at 175 % a DPI-unaware caller gets logical sizes and a cropped picture. The mock's default song is 261 s but LRCLIB's is 267 s, so plain `?mock` gets PetitLyrics; pass `|267000` for LRCLIB.
- Windows PowerShell 5.1 re-encodes text piped to a native command and breaks UTF-8, so `build-win.ps1` runs `node --check` through `cmd /c` with `<`. `.gitattributes` keeps `*.sh` LF, or Git for Windows (`core.autocrlf=true`) checks them out with CRLF and bash fails on them.
- `./serve.sh`, then `?mock` / `?mock=Artist|Title|durationMs&t=<s>` in a browser — the plain page has no player of its own. Never start or change anyone's real playback from an agent.
- `?mock` cannot reach the stream path: `MockPlayer` turns a duration of 0 into 261000.
- Frame timing in the Windows app: launch with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333 --disable-features=CalculateNativeWinOcclusion --disable-backgrounding-occluded-windows` or a window behind others gets no animation frames, then time animation-frame intervals and `J.Renderer.prototype.frame` over CDP. A mock that stops drawing has usually been paused by a click on the window — check the play button before suspecting the code.
- Count non-background pixels on the canvas before trusting a screenshot: two empty frames always compare equal.
- `window.jizuraSync.plan` / `.song` in devtools expose the current plan and lyric source.
- `node --input-type=module --check < web/app.js` (same for `lyrics.js`, `native.js`, `i18n.js`; `build-win.ps1` checks all four) before loading the page. A syntax error blanks the whole page with no UI at all — an apostrophe inside a single-quoted string on a path `?mock` never reached once did, so mock testing alone missed it.
- To test error handling in `?mock`, fail the network before the page loads: devtools `navigate_page` with an `initScript` that wraps `window.fetch` to reject `lrclib` URLs (and `petitlyrics` / `lrc.red` for an all-sources failure; NetEase goes through the host, not `fetch`, and the plain web page never asks it).
- `serve.sh` sends `Cache-Control: no-store`. Plain `python3 -m http.server` sends no cache headers, and Chrome then kept running an old `app.js` after edits; if you serve `web/` another way, hard-reload (Ctrl+Shift+R) before concluding a change did not work.
- The fullscreen button did not respond to a real click in the Chrome driven by the devtools MCP, but did via CDP and in the user's own Chrome. Confirm fullscreen in a normal browser.
